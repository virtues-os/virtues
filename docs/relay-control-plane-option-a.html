Relay control plane — Option A

atlas/virtues-api mints each box's name + token; the relay stays stateless and blind. Why it's the pick.

The flow

1 · Link / relay-enable — minting

The box asks for its relay identity over the channel that already exists (authenticated by api_key). atlas is the only party that touches the secret.

box → atlas
GET relay-config  (auth: api_key)
atlas computes
boxhash = H(box_identity_pubkey) → sni = "<boxhash>.virtues.ch" token = derive_token(RELAY_SECRET, sni) deterministic name (stable across reinstall) · dedicated box domain, isolated from virtues.com · ensures wildcard DNS *.virtues.ch → relay + ACME TXT
atlas → box
{ relay_addr, sni, token } box persists these in box_secrets. The master secret never leaves atlas.

2 · Runtime — registration

The relay re-derives the expected token from the one secret it holds. No lookup, no state.

box → relay
dial out 443 · Register{ sni, token } box has no public inbound port (CGNAT-safe)
relay verifies
expected = derive_token(RELAY_SECRET, sni) · ct_eq(token, expected) same secret shared atlas↔relay out-of-band · constant-time compare
relay → box
Registered ✓ box flips an in-process REGISTERED flag

3 · Pairing — only advertise a reachable URL

Clients get the relay URL only once the box is actually registered, so they never persist a dead URL over a working LAN origin.

client → box
pair / provision
box → client
box_url = REGISTERED ? "https://<sni>" : null carried on both ConsumeResponse and ProvisionResponse · client falls back to LAN origin when null
client ⇄ relay ⇄ box
E2E TLS — relay splices ciphertext, never decrypts

Why Option A wins

Relay stays blind & stateless
One secret, derives the expected per-SNI token on the fly. No per-box table → the RAM-only zero-knowledge property that is the privacy moat.
Box never holds the master secret
A compromised box gets only its own derived token — it cannot mint another tenant's SNI. Preserves the fail-closed auth fix.
Reuses an existing channel
Rides the api_key/link handshake atlas already runs. No new auth surface to design, secure, or rate-limit.

Trade-offs accepted

  • Lifecycle for free — relay access tracks the subscription/link state already managed.
  • Cadence — enablement could wait for a renew; fixed with a force-refresh on first relay-enable.
  • Secret rotation — relay accepts current + previous secret during a grace window; atlas re-mints on next fetch.

Why not B or C

  • B (dedicated endpoint) — same payload that can ride the existing claim/link call, for an extra surface to secure. Kept only as a fallback if we later want relay fully decoupled from billing.
  • C (per-box secrets) — makes the relay stateful and needs api↔relay sync + restart re-hydration. Sacrifices the exact blind/stateless property HMAC buys. Discouraged.
